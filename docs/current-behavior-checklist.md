## 运行方式

当前项目无 `package.json`、依赖安装、构建步骤或自动化测试。

### 直接打开

双击根目录 `index.html`。当前所有 CSS、SVG、菜品数据和 JavaScript 都内联，因此可在 `file://` 环境运行。外卖平台跳转和浏览器安全能力仍可能受浏览器策略影响。

### 本地静态服务器

```powershell
py -m http.server 8000
```

访问 <http://127.0.0.1:8000/>。macOS/Linux 使用 `python3 -m http.server 8000`。

### 线上

访问 <https://tuozhekongqi.github.io/Meal-Serendipity/>。当前站点请求成功时返回根目录单页应用，不需要服务端路由。

## 页面与导航基线

当前应用由五个互斥页面区域组成：

1. `pageCover`：古风封面，提供完整流程和快速摇签两个入口。
2. `pageForm`：人数、餐资、场景、逐人口味/主食、避讳和天气表单。
3. `pageMode`：选择“精择 · 三案呈上”或“随缘 · 摇一签”。
4. `pageResult`：显示三案或摇签结果。
5. `pageOrder`：显示已选菜品、平台搜索入口和复制关键词。

`showPage()` 通过添加/移除 `hidden` 切换页面，并把最后页面名写入 `wt_last`。初始化始终先显示封面；只有最后页面是 `pageOrder` 且存在已保存菜品时，刷新后才恢复下单页。

## 核心流程基线

### 快速摇签

- 点击“随便 · 不问口味”先出现确认弹窗。
- 确认后将人数设为单人、摇签范围设为 `free`，直接进入结果页并开始摇签。
- 每位食客抽取一条静态菜品；快速入口默认只有一位食客。
- 约 1.2 秒摇签动画后显示签条，再出现“签落 · 缘分已定”弹窗。
- 点击“认命，就吃这个！”后写入历史并进入下单页。

### 完整表单

- 人数必须显式选择单人、双人或多人。多人输入接受 1–50 的整数。
- 预算使用 4 个总餐资档，展示金额随人数相乘；内部仍以 1–4 档保存。
- 场景选项随单人、双人、多人切换，且为必填。
- 每位食客至少选择 1 个口味和 1 个主食类型；口味最多 3 个，按主味、次味、末味排列；每人只能选择 1 个主食类型。
- 多人可以逐人填写，也可将第 1 位的选择复制给后续食客。
- 避讳为选填，支持 21 个预设项和自定义关键词；自定义单字仅允许“辣 / 酸 / 甜”。
- 天气默认“晴”，可在 8 个展示选项中切换，内部映射为晴、雨、热等推荐倾向。
- 点击“落笔定案”时统一校验人数、多人数量、场景及每位食客的口味和主食；缺失时弹窗并滚动到相关区域。

### 推荐模式

- “精择 · 三案呈上”生成 `top`、`safe`、`niche` 三套菜单，显示为首选、稳妥、尝鲜。
- 每套菜单按食客逐人选菜；多人结果会显示菜品归属。
- 点击备选卡可将其升为主卡；只有当前主卡提供“择此一席”。
- “重择一餐”沿用相同条件重新生成三案，并尽量避开本轮已出现菜品。
- “随缘 · 摇一签”提供“在预算内摇”和“随心摇”。若预算内候选为空，会继续从通过其他硬过滤的候选中抽取。
- 两种模式都先调用同一个 `poolFor()`，因此当前避讳、口味和主食类型过滤共同生效。

### 下单与恢复

- 下单页按菜名构造美团外卖和淘宝闪购/饿了么 H5 搜索链接，不代表商家或菜品当前真实可售。
- 桌面和普通移动浏览器点击平台链接时先显示过渡层，再导航；微信内直接使用新窗口链接。
- 复制按钮使用 `document.execCommand('copy')`，失败时提示手动复制。
- 进入下单页后保存已选菜品、归属、三案和最近历史；刷新会恢复最后一次下单页。
- 摇签结果的三案值为 `null`。从恢复后的下单页返回结果页时，会提示签已散去并要求重摇。

## 当前数据与推荐算法

### 静态数据

- `DISHES` 内联于 `index.html`，共 175 条。
- 每条记录包含：`n` 名称、`t` 口味数组、`ty` 类型、`p` 价格档、`w` 天气倾向、`c` 大众/小众、`k` 食材关键词、`d` 描述。
- 共有 9 个主食类型。数据不包含商家 ID、门店位置、库存、销量、评分、配送距离、ETA 或实时费用。

### 过滤

- `banned()` 依据预设/自定义避讳匹配辣味、菜名和食材关键词。
- `poolFor()` 依次执行避讳、最高可用口味偏好和主食类型硬过滤。
- 候选充足时避开最近吃过的菜；历史最多保存 9 个名称。
- 若某位食客过滤后无候选，推荐和摇签都会阻止继续并要求调整。

### 评分

- 主味命中 `+45`，次味 `+28`，末味 `+12`，均未命中 `-8`。
- 主食类型命中 `+30`，所选类型未命中 `-10`。
- 价格档完全匹配 `+26`，相邻档 `+10`。
- 天气倾向命中 `+18`；潮湿且清淡额外 `+6`。
- 场景按口味、类型、价格、大众度、分享或精致倾向加 `+6` 至 `+12`。
- 多人场景统一 `+4`；需要避开本轮已选菜时 `-25`。
- `safe` 优先大众菜（`c === 1`），`niche` 优先小众菜（`c === 0`）。同分排序没有显式稳定键。

### 当前价格含义

- 单菜显示档：1=`10–15`、2=`15–25`、3=`25–40`、4=`40–60` 元。
- 表单第 4 档显示“40 元以上”，菜单合计却按单菜最高 65 元计算。这是现有口径不一致，作为基线记录，不在阶段 0 修复。
- 当前预算不包含配送费、包装费、起送价、优惠或多人共享菜品规则。

## 本地存储基线

| Key | 存储 | 用途 |
| --- | --- | --- |
| `wt_form` | `localStorage` | 表单、逐人偏好、天气、模式和摇签范围 |
| `wt_taboo` | `localStorage` | 避讳关键词数组 |

| `wt_last` | 两者 | 最后显示页面；恢复时优先 `sessionStorage` |

旧键 `wt_black` 会在初始化时迁入 `wt_taboo` 后删除。当前版本不会保存精确位置或远程账户信息。

## 后续变更的重复检查

每次业务或 UI 变更都应新建一份运行记录，并逐项确认：

- [ ] 首页两个入口可见且可操作。
- [ ] 快速摇签默认单人、自由预算，能够到达下单页。
- [ ] 完整表单缺失必填项时阻止继续并给出可定位的反馈。
- [ ] 单人完整流程可生成三案并选择任一方案。
- [ ] 双人和自定义多人能逐人保存偏好、生成对应菜品与归属。
- [ ] 预设避讳和自定义避讳在精择与摇签两条路径都不被绕过。
- [ ] 预算内摇签优先使用不高于预算档的候选；回退行为有明确记录。
- [ ] 重择、返回、回首页、重置全部条件的状态符合预期。
- [ ] 下单平台链接只包含必要菜名，复制成功/失败都有反馈。
- [ ] 刷新恢复最后下单页；损坏或缺失本地数据时安全回到首页。
- [ ] 320px、390px、768px、1440px 无页面级横向溢出。
- [ ] 键盘顺序、焦点可见、弹窗焦点、200% 缩放和减少动效经过检查。
- [ ] 控制台无新增错误；已知 favicon 404 只允许在后续部署阶段被修复，不能增加新错误。

## 已知问题与非目标

- 当前视觉为传统古风海报式，与已确认的极简智能型目标冲突；阶段 0 只记录，不改页面。
- 当前完整流程超过目标所需的最小输入量，无法保证 30 秒完成；阶段 0 不改流程。
- 首页文案称“默认单人”，但完整表单内部人数初始为空，仍要求显式选择；阶段 0 不改校验。
- 当前只是静态菜品灵感，不支持真实预算总价、距离、ETA、营业或库存。
- 多数选择按钮未维护 `aria-pressed`，自制弹窗缺少完整对话框语义和焦点管理，且未实现减少动效；阶段 0 不修复。
- 当前缺少 favicon，浏览器控制台会出现 404；计划在部署质量阶段处理。
- 当前没有自动化测试、构建产物隔离或 GitHub Actions 质量门。
