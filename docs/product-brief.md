# 产品简述

## 一句话定位

“一餐之缘”用少量问题和带仪式感的推荐流程，帮助个人或多人快速决定今天点什么外卖，并直接进入外卖平台搜索。

## 用户与场景

- 不知道吃什么、容易在外卖列表中反复浏览的个人用户。
- 需要兼顾多人不同口味、主食和忌口的小组。
- 希望在预算、天气或聚餐场景约束下获得可执行建议的用户。

## 核心用户任务

1. 快速决定：跳过详细设置，直接随缘摇签。
2. 精准决定：填写人数、预算、场景、逐人口味/主食、饮食避讳和天气，获得三套方案。
3. 安心决定：确认推荐没有触犯忌口或过敏原，并理解推荐理由。
4. 立即行动：选择菜品后前往外卖平台搜索，或复制菜名。

## 当前产品体验

- 入口：根目录 `index.html`。
- 精择流程：封面 → 条件表单 → 模式选择 → 首选/稳妥/尝鲜 → 下单页。
- 随缘流程：封面或模式选择 → 预算内/随心范围 → 每人一签 → 下单页。
- 数据保存在浏览器 `localStorage` / `sessionStorage`，无后端和遥测。
- 菜品库当前包含 175 个条目、9 类主食/餐食类型。

## 产品原则

- 先减少决策成本，再提供丰富度。
- 避讳和过敏原是硬约束，不能被随机性或候选池回退绕过。
- 多人偏好按人保留，不用“平均口味”替代真实差异。
- 推荐理由真实、简短、可解释。
- 现代、简洁、舒服的移动端体验优先；中式仪式感服务于决策，不喧宾夺主。
- 默认保持零依赖、可离线、数据留在本机。

## 非目标

- 当前不做餐厅库存、配送时效或实时价格聚合。
- 当前不做账号、社交关系、支付和订单履约。
- 当前不承诺医学级过敏安全；产品应明确数据覆盖边界，鼓励用户下单前再次确认商家配料。
- 不以引入框架或重做页面作为独立目标。

## 成功信号

- 用户能在短流程内选定一餐并进入下单搜索。
- 硬约束违规为零，候选池不足时给出明确可恢复提示。
- 单人和多人主流程在常见手机宽度上均可顺畅完成。
- 推荐结果具有适度变化，同时能说明为什么适合当前条件。
- 刷新后合理恢复状态，不泄露或上传用户偏好。

## 待确认问题

- 根目录版本与 `一餐之缘_分享版/` 的长期权威关系和发布流程。
- 实际部署平台、公开 URL 和发布责任人。
- 外卖平台跳转链接在不同设备、微信内置浏览器和地区的可用性。
- 菜品与过敏原标签的维护来源、审核标准和免责声明。
