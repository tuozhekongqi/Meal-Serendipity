# Meal-Serendipity 产品方案

状态：已确认，可进入分阶段实施。最后更新：2026-08-17。

## 产品定位

Meal-Serendipity 是一个面向外卖选择困难用户的轻量决策助手：用尽可能少的输入，从当前可用候选中给出一个可执行的首选，并清楚说明为什么推荐它。

核心承诺：用户打开网页后，应在约 30 秒内得到一个符合总预算、口味、距离、配送时间、饮食避讳和当前状态的外卖推荐；回访用户在沿用偏好时应在 10 秒内得到结果。

## 产品决策

- 从“有仪式感的随机菜品工具”转向“快速、可信、可解释的外卖决策工具”。
- 默认只给一个首选；“更快、更便宜、更新鲜”作为明确替代，不再先让用户选择推荐模式。
- 完整模式必须推荐真实可下单候选，包含商家、菜品、含配送费总价、距离、预计送达和营业/可售状态。
- 没有实时候选数据时只能进入“菜品灵感模式”，且必须明确说明距离、配送时间和实际价格需要在外卖平台确认。
- 忌口和过敏原是不可自动放宽的硬约束；随机模式同样不得绕过。
- 当前传统古风海报式视觉停止延续。新视觉采用“极简智能型”，中式印章、宣纸、楷体、古风标题和摇签仪式不再作为主界面语言。
- 主流程优先服务单人快速决策；多人模式保留为次级入口，避免拖慢 30 秒主目标。

## 目标用户

- 在外卖平台反复浏览、难以做决定的个人用户。
- 在通勤、加班、深夜、天气不佳等状态下，希望快速获得合适选择的用户。
- 有明确预算、送达时间或饮食避讳，需要先排除不合适候选的用户。
- 次级用户：希望兼顾多人偏好的小组。

## 核心用户任务

1. 确认送达区域，设置总预算和最晚送达时间。
2. 用一个选项表达当前优先目标，例如“快一点”“便宜一点”“吃得满足”“清淡舒服”“想吃点新的”。
3. 沿用或修改口味、忌口和人数。
4. 获得一个首选，并快速理解硬条件、匹配理由和必要取舍。
5. 前往外卖平台下单；不喜欢时换一个，而不是重新填写整套表单。

## 产品模式

### 实时外卖模式

适用条件：已获得合法、稳定且足够新鲜的商家与菜品候选数据。

结果必须展示：

- 商家和菜品名称；
- 含配送费的预计总价；
- 距离；
- 预计送达时间；
- 营业和可售状态；
- 至少两条可验证的推荐理由；
- 数据更新时间和必要取舍。

### 菜品灵感模式

适用条件：实时数据不可用、定位被拒绝或供应方异常。

结果只承诺菜品方向与偏好匹配，不得声称满足真实距离、ETA、营业状态或订单总价。界面必须显示“灵感模式”及平台二次确认提示。

“精择 / 摇签”独立模式页从主流程移除；完全随机可作为首页次级操作保留。

## 主用户流程

### 新用户

1. 打开首页，看到“30 秒，选好这顿外卖”。
2. 允许定位或手动选择送达区域。
3. 确认默认预算、最大配送时间和当前优先目标。
4. 必要时展开口味与忌口。
5. 点击“给我一个推荐”。
6. 查看首选、满足条件和推荐理由。
7. 点击“去下单”或“换一个”。

### 回访用户

1. 读取本地保存的非敏感偏好和上次条件。
2. 用户确认位置摘要与当前优先目标。
3. 一次点击获得推荐。

### 无候选

1. 明确说明没有候选满足哪些条件。
2. 一次只建议放宽一个软条件，例如配送时间或预算。
3. 不建议放宽忌口和过敏原。
4. 实时数据不可用时，允许用户主动切换到菜品灵感模式。

## 功能优先级

### P0：首个可用版本

- 定位或手动区域输入，以及定位失败降级。
- 含配送费的总预算。
- 最大配送时间和最大距离。
- 当前优先目标。
- 口味与忌口本地保存。
- 硬过滤、结构化评分和解释。
- 一个首选、“换一个”和平台跳转。
- 实时模式与灵感模式的清晰区分。
- 核心推荐规则的确定性自动化测试。
- 320px 至桌面端响应式与 WCAG 2.2 AA 核心要求。

### P1：重要增强

- 时间段与天气自动上下文。
- “更快、更便宜、更新鲜”三个替代候选。
- 最近选择去重和历史页。
- 多人简化模式。
- 商家/菜品数据新鲜度与异常降级。
- 端到端浏览器测试、PR 检查和自动部署。

### P2：验证后再做

- 收藏或跨设备账号同步。
- 营养偏好和更细的份量模型。
- 社交分享和城市内容专题。
- 轻量随机或情绪化互动。

## 推荐规则

### 硬过滤

- 商家营业且菜品可售；
- 不命中忌口或过敏原；
- 含配送费总价不超过预算；
- ETA 不超过用户上限；
- 距离不超过用户上限；
- 候选数据未超过配置的数据新鲜度阈值，默认阈值为 5 分钟。

### 软评分

默认权重：口味 25%、配送速度 20%、当前状态 15%、预算利用率 15%、距离 10%、商家质量 10%、新鲜感 5%。用户选择“快一点、便宜一点、吃得满足”等目标时，只调整相应权重，不增加新的表单步骤。

推荐结果使用“非常匹配 / 比较匹配 / 有一项取舍”等级，不显示虚假精确的小数分数。解释由结构化原因代码生成，必须与实际过滤和评分贡献一致。

## 数据边界

- 浏览器端负责交互、偏好保存、展示和可在本地运行的推荐计算。
- GitHub Pages 不保存私密 API key，也不承担受保护供应商接口的签名或代理。
- 实时候选通过单独的合法数据服务提供；前端通过稳定的 `CandidateProvider` 接口消费。
- 精确位置只用于当前请求；默认不长期保存坐标，只保存用户主动选择的粗粒度区域或偏好。
- 过敏原标签不能替代商家配料确认，结果页必须提示用户下单前再次确认。

## 成功指标

- 新用户从打开页面到看到首选的中位时间不超过 30 秒。
- 回访用户在复用偏好时的中位时间不超过 10 秒。
- 自动化约束测试中已知忌口、预算、ETA 和距离违规为零。
- 每个首选至少显示两条真实原因；存在取舍时必须显示一条取舍说明。
- 320px、390px、768px 和 1440px 无横向溢出，主要流程可用键盘完成。
- 主推荐接受率、换一换率、无候选率和平台跳转率可用于评估效果；引入遥测前必须先确定隐私方案并获得批准。

## 非目标

- 不处理支付、订单履约、退款或客服。
- 不抓取、伪造或绕过授权获取外卖平台数据。
- 不承诺医学级过敏安全。
- 不在首个版本中建设社交网络、复杂账号体系或城市内容媒体。
- 不以引入前端框架、动画或视觉重做本身作为成功标准。

## 已解决的冲突与外部依赖

- 零后端、完全离线与真实距离/ETA 不可同时完整满足：最终方案以实时模式完成产品承诺，以灵感模式提供明确降级。
- 当前古风视觉与已确认方向冲突：新设计系统以极简智能型为唯一目标方向。
- 多人深度定制与 30 秒目标冲突：多人功能降为 P1 次级流程。
- 真实数据供应方不属于本仓库能力。代码实施可以先完成 provider 契约和测试适配器；启用实时模式必须以获得合法数据源和服务端地址为准，未满足时默认使用灵感模式。
